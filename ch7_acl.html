第 7 章

ACL 存取控制

用 policy 檔決定「誰能連誰」。讀完這章，你會寫出預設全拒、只放行必要互連的 ACL，把私有網段守得滴水不漏。

網段安全的最後一道閘

裝置能加入網段，不代表它應該能連到每一台。ACL（Access Control List，存取控制清單）決定了節點之間的連線規則。預設該是「全部拒絕」，你只放行真正需要的互連，這就是最小暴露。

本章任務：看懂 policy 檔、寫出允許特定使用者互連的 ACL，並理解預設全拒的意義。
開太寬 = 沒防線：若 ACL 放行「全部連全部」，等於任何一台被攻破，整張網都淪陷。寧可先全拒，再一條條放行。

policy 檔與 hujson

Headscale 的 ACL 寫在一份 policy 檔裡，格式是 hujson（Human JSON）：長得像 JSON，但允許註解（//）與尾端逗號，方便你邊寫邊加說明。

這份檔案在 Headscale 的設定檔（config.yaml）裡由 policy.path 指定，啟動時載入。改動後要重新載入（重啟服務或依部署方式）才會生效。

心智模型：policy 檔就是「網段的交通規則」——沒有明寫放行的，一律禁止通行。

預設全拒，逐條放行

一份最小、最安全的 policy 檔長這樣——只有結構，沒有任何放行規則，代表預設全拒：

{
  // 使用者群組（把多個 user 歸成一組）
  "groups": {
    "group:family": ["alice", "bob"],
  },

  // 存取控制：這裡沒寫 = 全部拒絕
  "acls": [
    // 之後才一條條加入你要放行的互連
  ],
}
先求不開，再求方便：一開始就放空 acls，確保預設全拒。等需要某個互連時，再加那一條。

六步寫出最小 ACL

  1. 先盤點「誰要連誰」

    列出你真正需要的互連，例如「家人的裝置互相能連」「手機能連到家裡 NAS」。不需要的一律不放。

  2. 把使用者分群組

    在 groups 裡把相關 user 歸成 group:family 之類的群組，之後用群組寫規則更清楚。

  3. 寫第一條放行

    在 acls 加一條 { "action": "accept", "src": ["group:family"], "dst": ["group:family:*"] }，允許群組內互連。

  4. 逐步加需要的規則

    只加你盤點過的互連。每加一條都問：「這條真的需要嗎？」

  5. 套用並重新載入

    把改好的 policy 檔放回 policy.path 指定位置，重啟 Headscale 服務（或依部署方式重載）讓它生效。

  6. 驗證

    實際測一條該通的、測一條不該通的。該通的不通、或該拒的卻通，都是規則有問題。

語法要精準：hujson 少了逗號、引號就整份不生效。改完用工具檢查格式，或用 Headscale 啟動時的 log 確認有無載入錯誤。

群組（groups）與標籤（tags）

寫 ACL 時有兩個好用的工具：

工具用途例子
群組 groups把多個 user 歸一組，規則寫給整組group:family
標籤 tags給服務／裝置打標籤，規則寫給標籤tag:server、tag:nas
用群組和標籤，別寫死單一 user：之後加人、加裝置，只要把它歸進既有群組或標籤，ACL 不用大改。

ACL 常見卡關

  1. 改了 policy 沒生效

    確認有重新載入（重啟服務）；看啟動 log 有沒有 hujson 語法錯誤。

  2. 該通的連不上

    檢查 src／dst 有沒有拼錯群組名或 user；群組名、標籤名要一致。

  3. 該拒的卻通了

    可能前面有較寬的規則先匹配。ACL 是逐條判斷，把「全拒」放在底線、避免放行範圍過大。

  4. 不確定某條該不該開

    預設不開。等真的有需求、也講得出理由，再開那一條。

ACL 常見問題

預設真的是全拒嗎？
對，policy 沒寫放行就預設拒絕。這是刻意設計，確保你不會不小心開太寬。
群組和單一 user 寫規則差在哪？
群組讓規則好維護：加人只要歸組，不用改 ACL。單一 user 適合特例。
ACL 會影響速度嗎？
不會。ACL 決定「能不能連」，實際流量仍走裝置間點對點加密，不經控制層轉發。
可以讓某台只出不進嗎？
可以，用 src／dst 的方向與 * 通配控制，例如只允許某裝置連出、不讓別人連它。
policy 檔要備份嗎？
要。它是網段規則的命脈，和 preauth key 一起納入備份，重建時才不會漏。
