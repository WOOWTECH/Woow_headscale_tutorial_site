Chapter 11

Security and minimal exposure

Go through the control server's entry point, preauth keys, the ACL (access control list) and your node inventory in one systematic security check. By the end of this chapter, you'll know which habits keep a private tailnet safe, which "conveniences" are really over-exposure, and how to shrink the exposed surface to the minimum.

A leaked key is the worst thing for a private tailnet

The security of your whole Headscale tailnet rests on a few things: the control server's entry point, preauth keys, and the ACL rules. Miss any one of them and an outsider can slip into your "private" tailnet. Security is not something you set up once; it is a handful of habits you keep up over time.

Chapter task: Check the entry point, the keys, the ACL and the nodes one by one, and close down the exposure you do not need. Everything here is tightening only; nothing deletes data.

Three lines of defense

Line of defenseWhat it protectsYour responsibility
Control server entry pointWho can reach the admin interface / APINever exposed to the public internet, admins only
preauth keyWho can add a device to the tailnetTreat it as a top secret and revoke it once it has been used
ACL (policy)Which devices can reach whichDefault deny; allow only the connections you actually need
The minimal-exposure principle: nothing is open by default. When you do open something, open it just enough to work, and keep the ability to revoke it.

Six-step security checklist

  1. Check that the control server is not exposed

    Confirm the admin interface / API is reachable only from your local network or through a controlled entry point, and is not open to the whole internet.

  2. Take inventory of your preauth keys

    Run headscale preauthkeys list to see which keys are still unused, and revoke the ones you no longer need right away.

  3. Check that the ACL is minimal

    Run headscale policy get to review the rules and confirm it is not an "allow everything" policy, leaving only the connections you need (Chapter 7).

  4. Take inventory of your nodes

    Run headscale nodes list to see which devices are there; if there is a node you do not recognize, disable it first and investigate afterwards.

  5. Check keys and accounts

    Do not hand the admin account around, and if you use an API key, rotate it regularly too.

  6. Confirm backups are running

    Config, policy and the database should all be backed up on a schedule (Chapter 10), and you should have done a restore drill.

If you see a suspicious node: when you spot a device or a key you do not recognize, revoke the key and disable the node first, then trace where it came from. Do not put it off.

Managing preauth keys

A preauth key is the "pre-authorized key" that lets a device join the tailnet. Anyone who gets hold of it can attach a device to your tailnet. The rules for managing them:

  • One key per machine, revoked once used: do not use one key over and over, and do not share it.
  • Never post it in the open: do not put a key in a group chat, and do not commit it to a repo.
  • Take inventory regularly: revoke every key that is "already used" or "no longer needed".
If a key leaks: revoke that key immediately, check whether any unknown node joined with it, and tighten the ACL if you have to.

Minimizing the ACL

The ACL (policy) decides "who can reach whom, and on which ports". The safest mindset is "default deny, allow by whitelist":

ApproachWhat it means
Default denyAnything not explicitly allowed is denied
Allow only the connections you needFor example, "the phone can reach HA at home, and nothing else"
Partition by userFamily devices and work devices stay apart, with no crossing over
Verify after every change: once the ACL is edited, test from an actual device that "what should connect connects, and what should not does not". Do not just look at the config and assume it is right.

Node inventory

Listing your nodes on a regular basis is like taking stock of "who is on the home tailnet". The key points:

  • You should recognize every node (its name, the device, what it is for).
  • A node you do not recognize: disable it first, then trace who added it and with which key.
  • A device that has not been online for a long time: confirm whether it is still needed, and remove it if it is not.
Do not leak information in node names: use names you can recognize but that give nothing away, and keep full personal names, addresses and serial numbers out of a node name.

Common security pitfalls

  1. You suspect a key has leaked

    Revoke that key immediately, go through your nodes and the recent join records, and if you have to, tighten the ACL and tell your users.

  2. You find an unknown node

    Disable the node, revoke the suspicious key, then work out where it joined from.

  3. The ACL is too wide and you want to tighten it

    List the connections you actually need first, allow them one rule at a time and deny the rest; verify for real once the change is in.

  4. You are not sure whether something should be open

    The default is "do not open it". When in doubt, leave it closed.

Security FAQ

What happens if someone scans the control server?
If the admin interface / API is exposed to the internet, an attacker can try to log in or to enumerate what is there. That is exactly why the control server stays on your local network and is never exposed to the public internet.
Can a preauth key be reused?
It can, but we strongly advise against it. One key per machine, revoked once used, is the safest pattern; sharing one key makes revoking and tracing harder.
What is the risk of an allow-everything ACL?
It means every device on the tailnet can reach every other one on every port. If any single device is compromised, the whole tailnet can fall with it. Keep it minimal.
How often should I take inventory?
We suggest a quick pass once a month (keys, nodes, ACL); when something is off (an unknown node, a suspected key leak), check right away.
Does the admin account need special protection?
Yes. Admins can change the policy and delete nodes. Use a strong password, do not hand it around, and rotate the API key regularly.
