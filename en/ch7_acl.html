Chapter 7

ACL access control

Use the policy file to decide "who can connect to whom". By the end of this chapter, you'll be able to write an ACL that denies everything by default, allows only the connections you actually need, and keeps your private tailnet watertight.

The last gate on tailnet security

A device being able to join the tailnet does not mean it should be able to reach every other device on it. An ACL (access control list) sets the rules for connections between nodes. The default should be "deny everything", and you allow only the connections you actually need. That is minimal exposure.

Chapter task: make sense of a policy file, write an ACL that lets specific users connect to each other, and understand what default deny is for.
Too wide = no defense: if your ACL allows "everything to everything", then the moment one machine is compromised the whole tailnet falls with it. Better to deny everything first, then allow one rule at a time.

The policy file and hujson

Headscale keeps its ACL in a policy file, written in hujson (Human JSON): it looks like JSON, but it allows comments (//) and trailing commas, so you can add notes as you write.

In the Headscale config file (config.yaml), policy.path points at this file, and it is loaded at startup. After you change it, it has to be reloaded (restart the service, or whatever your deployment method calls for) before the change takes effect.

Mental model: the policy file is "the traffic rules for your tailnet" — anything not explicitly allowed is denied.

Default deny, allow one rule at a time

The smallest and safest policy file looks like this — structure only, no allow rules at all, which means everything is denied by default:

{
  // User groups (put several users in one group)
  "groups": {
    "group:family": ["alice", "bob"],
  },

  // Access control: nothing listed here = deny everything
  "acls": [
    // Add the connections you want to allow, one rule at a time
  ],
}
Closed first, convenient second: leave acls empty at the start, so default deny is guaranteed. When you actually need a particular connection, add that one rule.

Six steps to write a minimal ACL

  1. Take inventory of "who needs to reach whom"

    List the connections you actually need, for example "the family's devices can reach each other" and "the phone can reach the NAS at home". Anything you do not need stays closed.

  2. Put your users into groups

    Inside groups, collect the related users into a group such as group:family. Writing the rules against a group after that is much clearer.

  3. Write the first allow rule

    Add one entry to acls: { "action": "accept", "src": ["group:family"], "dst": ["group:family:*"] }. That lets the members of the group connect to each other.

  4. Add the rules you need, one at a time

    Only add the connections that were on your inventory. Each time you add one, ask: "Is this rule really necessary?"

  5. Apply and reload

    Put the edited policy file back at the location policy.path points to, then restart the Headscale service (or reload it the way your deployment does) so it takes effect.

  6. Verify

    Actually test one connection that should work and one that should not. If something that should connect cannot, or something that should be refused gets through, the rules are wrong.

Syntax must be exact: one missing comma or quote and the whole hujson file stops working. After editing, check the format with a tool, or read the Headscale startup log to see whether it failed to load.

Groups and tags

Two tools make an ACL easier to write:

ToolWhat it is forExample
GroupsPut several users in one group and write the rule for the whole groupgroup:family
TagsTag a service or a device and write the rule for the tagtag:server, tag:nas
Use groups and tags, not hard-coded users: when you add a person or a device later, you only have to put it into an existing group or give it an existing tag, and the ACL barely changes.

Common ACL pitfalls

  1. You changed the policy and nothing happened

    Confirm that it was reloaded (restart the service); check the startup log for a hujson syntax error.

  2. Something that should connect cannot

    Check whether the group name or the user in src/dst is misspelled; group names and tag names have to match exactly.

  3. Something that should be refused gets through

    A broader rule earlier in the file may have matched first. An ACL is evaluated one rule at a time, so keep "deny everything" as the baseline and avoid rules that allow too much.

  4. You are not sure whether to open a rule

    Leave it closed by default. Open that one rule when there is a real need and you can explain why.

ACL FAQ

Is the default really deny everything?
Yes. If the policy does not allow a connection, it is denied. That is deliberate: it makes sure you never open things too wide by accident.
What is the difference between writing a rule for a group and for a single user?
Groups keep the rules maintainable: to add a person you only put them in the group, without touching the ACL. A single user fits a special case.
Does an ACL affect speed?
No. The ACL decides "whether a connection is allowed"; the traffic itself still runs peer-to-peer and encrypted between the devices, and is not relayed through the control server.
Can I let one machine connect out but not in?
Yes. Use the direction of src/dst together with the * wildcard, for example allowing one device to connect out while nobody else is allowed to connect to it.
Should I back up the policy file?
Yes. It holds the rules for your tailnet and is one of the things you cannot lose. Back it up together with your preauth keys, so nothing is missing when you rebuild.
