Chapter 10

Admin settings

Get to know Headscale's admin settings: policy, DERP relays, users (namespaces) and version updates. By the end of this chapter, you'll be able to maintain the whole tailnet as its admin, keep your backups in order, and update the version safely.

This chapter is for admins

Headscale is the brain of the whole tailnet. Users joining, who can reach whom, the relay servers, version updates — an admin maintains all of it. This chapter is a practical reference for the admin; if you are an ordinary user, the concepts are enough.

Admin actions affect the whole tailnet: changing the policy, touching DERP, updating the version — every one of them affects all the devices that are already connected. Confirm the blast radius before you touch anything. If you're not sure, don't change it.

What admins manage

Headscale's settings fall into a few areas, and you manage most of them through config.yaml and the command line (CLI):

AreaWhat it coversCommon actions
policy (ACL)Who can reach whom, which ports are allowedView, import, minimize access
DERPThe list of relay serversCheck the relays are usable, optionally self-host DERP
Users / namespacesThe grouping a device belongs toCreate, list, manage
Version updatesUpgrading Headscale itselfRead the release notes, back up, then update
The CLI is the main entry point: most Headscale admin actions are done with the headscale command line. Some environments have a Web UI, but the CLI is the most reliable and the best documented.

Five steps for a routine maintenance pass

  1. List the users and nodes

    Use headscale users list and headscale nodes list to take inventory of which accounts and devices are currently on the tailnet.

  2. Review the policy

    Use headscale policy get to look at the current access rules and confirm nothing is opened too wide (Chapters 7 and 11).

  3. Check the keys

    Use headscale preauthkeys list to take inventory of the keys that have not been used yet, and revoke the ones you do not need.

  4. Look at the service status

    Confirm the Headscale service is healthy, the DERP relays are reachable, and the log shows no recurring errors.

  5. Take a backup

    Include config.yaml, the policy and the database in a regular backup (covered later in this chapter).

Least privilege: admins can change the policy and delete nodes. Do not hand out admin accounts freely; keep the number as small as you can.

DERP relay servers

DERP (the relay protocol) is the fallback channel for when a direct peer-to-peer connection between two devices fails. Normally traffic takes a direct, encrypted peer-to-peer connection; it falls back to a DERP relay only when a direct connection cannot be made (for example symmetric NAT, or a firewall blocking it).

DERP sourceWhat it meansWatch out
Built-in DERPHeadscale can embed one DERP serverLeast work, but it is a single point and performance is limited
External DERP listThe config file points at a set of public DERP serversScales well, but traffic passes through a third-party relay
Self-hosted DERPYou run your own DERP server and add it to the listBest control, but extra maintenance
Rule of thumb: if two devices can connect directly, let them (fast, no relay in the path); rely on DERP only when they cannot. A relay is a fallback, not the normal path.

Managing users (namespaces)

Headscale groups devices by "user" (early versions called this a namespace). One user can own several nodes, and the policy can draw its lines by user too. Newer versions renamed namespace to user; the concept is the same.

  • Create: headscale users create <name>
  • List: headscale users list
  • What it is for: keep "family devices" and "work devices" managed separately, each with its own keys and its own policy scope.
Do not mix old and new names: command names changed between versions (namespace ↔ user), so before you run anything, check the docs for your version instead of copying an older tutorial.

Back up policy, keys and config

What you cannot lose in Headscale is not the nodes themselves, but these few things — rebuilding the whole tailnet depends on them:

  • config.yaml: the server settings (including DERP, what it listens on, and where the database lives).
  • policy (ACL): the access rules, the core of your security.
  • Database: the state of users, nodes, keys and so on.
Verify your backups: a backup you have never restored does not count. Run a restore drill on a regular schedule and confirm you really can rebuild the tailnet.

Version updates

  1. Read the release notes first

    Always read the official release notes before you update, and watch for breaking changes between versions (for example renamed commands, or a changed config file format).

  2. Back up first

    Back up config.yaml, the policy and the database before you update. That is a prerequisite.

  3. Pick an off-peak window

    An update briefly interrupts the control server, so pick a time when nobody is using the tailnet.

  4. Verify after the update

    Once it is updated, list the nodes, test a connection between devices and confirm the policy is in effect.

Do not skip versions: do not jump straight from a very old version to the latest; there may be several incompatible changes in between. Upgrade step by step, the way the official docs recommend.

Common admin pitfalls

  1. The command is missing, or its usage changed

    Headscale commands evolve from version to version (namespace → user, acl → policy, for example). Check the docs for your version instead of copying an older tutorial.

  2. A device cannot reach DERP

    Confirm the DERP list is reachable and the firewall allows it; the log is the place to look first for clues about why the relay failed.

  3. The policy change did not take effect

    Confirm the policy was imported/saved correctly, and run the relevant checks again; some changes only take effect once the nodes resync.

  4. Nodes are offline after an update

    Usually a config or compatibility change. Read the release notes first, then check the log and the node status.

Admin FAQ

Can ordinary users change these settings?
No. Policy, DERP, users and version updates are all admin-level. An ordinary user only deals with whether their own device can connect.
Are namespace and user the same thing?
Same concept: both are a way to group devices. It was called namespace early on and renamed to user in newer versions, and the commands changed with it, so check the docs for your version before you run anything.
Do I have to self-host DERP?
Not necessarily. In most cases the built-in or an external DERP is enough; self-host it only when you need more control and more privacy.
Will an update disconnect my devices?
The control server is briefly interrupted during an update, and peer-to-peer connections that are already established may be affected. Pick an off-peak window and back up first.
Does the database need its own backup?
Yes. Users, nodes and keys all live in the database, so backing up the config on its own is not enough. You need both.
